# 开发难点与思路转变

这份文档用于面试复盘，不是运行手册。

## 1. 从聊天 demo 转向工程平台

最开始容易把 RAG 做成一个“上传文档然后聊天”的 demo。但大厂面试更关心的是线上链路：

- 检索不准怎么排查；
- 用户连续追问怎么保留状态；
- 工具调用怎么鉴权；
- 节点执行慢怎么展示进度；
- 服务重启后怎么恢复；
- 如何统计任务成功率和工具选错率。

因此这个项目的设计重点从“模型回答”转为“链路可控”：把 understand、retrieve、rerank、tool、answer 拆开，每一步都有状态和事件。

## 2. 记忆不应该全部向量化

一开始很容易把所有对话历史都塞进向量库。这样在 demo 里可以跑，但实际有几个问题：

- 越聊越慢；
- 过期事实很难删除；
- 相似但冲突的记忆会污染回答；
- 当前任务状态和长期偏好混在一起。

现在的设计是：

- Redis 保存短期会话和 checkpoint 指针；
- 向量库只保存长期语义知识；
- trace / 工具日志单独保存；
- 反思经验单独进入经验库。

## 3. RAG 排查不能只改 prompt

RAG 答非所问时，最常见的错误是直接改 prompt。实际排查顺序应该是：

1. 文档清洗是否破坏结构；
2. chunk 是否过大或过小；
3. overlap 是否覆盖关键上下文；
4. embedding 是否适合中文和业务语料；
5. metadata filter 是否误过滤；
6. top_k 是否合理；
7. 是否缺少 BM25 / SQL / 图谱多路召回；
8. reranker 是否把关键证据排上来；
9. prompt 是否要求引用证据。

这个项目保留了 Evidence API，后续替换召回组件时不影响上层 workflow。

## 4. SSE 不只是用户体验，也是 observability

Agent 调用链比较长，用户只看到最终答案时，很难判断系统卡在哪里。SSE 事件可以展示：

- 当前执行到哪个节点；
- 召回了多少证据；
- 调用了哪个工具；
- 工具是否失败；
- 最终引用了哪些证据。

这对调试、监控和面试讲解都很重要。

## 5. 工具 schema 必须做业务校验

Function Calling 或 MCP 只能保证模型输出接近 schema，并不能保证业务合法。例如：

- 参数类型合法，但订单不是当前用户的；
- 工具可以调用，但当前意图不允许；
- 查询结果来自旧缓存；
- 工具返回被提示注入污染。

所以项目里工具 registry 增加了 `allowed_intents` 和结构化错误码。生产版还要增加租户、用户、权限、幂等和超时控制。

## 6. 为什么先做轻量实现

这个仓库当前不是为了追求复杂，而是为了让面试官能快速看懂你会设计什么：

- API 边界清楚；
- 状态字段清楚；
- 事件流清楚；
- 扩展路径清楚；
- 文档能讲真实问题。

后续如果需要，可以把轻量 keyword retriever 换成 Milvus / pgvector，把 workflow 换成 LangGraph，把 memory 换成 Redis Cluster。
